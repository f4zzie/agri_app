## Notes

- **Buyer dashboard:** the estimated `rows` goes *up* while the time drops. With `idx_crops_status_created` the optimizer reads available listings already in `created_at` order and stops after `LIMIT` rows; `rows` reports the size of the range, not the rows actually read. Before, every farmer was joined, the result put in a temporary table and sorted.
- **Marketplace by county:** no index added. `county_id` is already selective and served by the index InnoDB created for `fk_users_county`. A composite `(role, county_id)` index was tried; the plan and timing did not change, so it was left out (indexes cost space and slow every write).
- **Farmer dashboard / activity log:** the gain is removing `Using filesort`; at a few dozen rows per user the absolute time difference is small, but it no longer grows with the user's history.

## Reading the plans

- `type: ALL` is a full table scan; `ref`/`range`/`const` mean an index narrowed the rows first.
- `Using filesort` means rows were sorted after reading; an index in `ORDER BY` order removes it, so `LIMIT` can stop early.
- `rows` is the optimizer's estimate of rows to examine for that table.
